# Sync cube-core with upstream Cube v1.7.33 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merge upstream `cube-js/cube` `v1.7.33` into `cube-core`'s `master` (via a `sync/v1.7.33` branch), preserving all 87 files of fork-specific customizations, and land it as a reviewed PR with green builds/tests.

**Architecture:** This is a git-merge integration task, not new-feature development — there's no new business logic to design, only existing fork behavior to carry through 615 upstream commits of change. Tasks are decomposed by package/area so each has an independently verifiable deliverable (that area's own build/tests), but they are **not independent worktree work**: they all operate on the *same* `git merge` in progress on `sync/v1.7.33`, so they execute sequentially in one working tree, in task order. A merge is a single atomic commit — intermediate conflict-resolution tasks end with `git add <files>` (staging), not `git commit`; the actual merge commit happens once, at the end of Task 13, after every conflict is resolved.

**Tech Stack:** Yarn workspaces + Lerna (TypeScript/JS), Cargo workspaces (Rust: `rust/cube`, `rust/cubesql`, `rust/cubestore`), Jest (unit/integration tests), Docker.

**Spec:** [docs/superpowers/specs/2026-09-03-cube-v1.7.33-sync-design.md](../specs/2026-09-03-cube-v1.7.33-sync-design.md)

## Global Constraints

- Merge source: `v1.7.33` tag fetched from `https://github.com/cube-js/cube.git` (the `upstream` remote's SSH URL is not reachable from this machine — fetch via HTTPS instead).
- Merge base: commit `68b870ea35da5c4b3ce275e1042a1cddb6186e75` (tag `v1.6.49`) — exact merge-base of `master` and upstream `v1.7.33`.
- All work happens on a new branch `sync/v1.7.33`, created from `master`, **except** Task 1 (build-artifact cleanup), which goes directly on `master` first.
- General conflict-resolution rule for every task below: where upstream changed code we haven't touched, take upstream's version. Where our fork added something upstream doesn't have (new functions, new branches, new packages), keep ours additively. Where both sides changed the *same* lines, preserve the fork's custom behavior (see spec's "Custom functionality inventory") while adopting upstream's surrounding refactor/structure — never silently drop a fork-specific behavior to resolve a conflict.
- After every conflict-resolution task, run that package's existing test command (given per task) before staging — if a pre-existing test fails because of the resolution, fix the resolution, not the test.
- Do not resolve `yarn.lock` by hand at any point — it is deliberately left conflicted until Task 13, where it's regenerated via `yarn install`.
- Rust toolchains already match between `master` and `v1.7.33` (`rust/cube`: `1.90.0`, `rust/cubesql`: `1.90.0`, `rust/cubestore`: `nightly-2025-08-01`) — no toolchain migration needed.
