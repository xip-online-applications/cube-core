# Sync cube-core with upstream Cube v1.7.43 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merge upstream `cube-js/cube` `v1.7.43` into `cube-core`'s current
branch (`claude/cube-upstream-sync-bb42ea`), preserving all 105 files of
fork-specific customizations, and land it as a reviewed PR with green
builds/tests.

**Architecture:** This is a git-merge integration task, not new-feature
development. Tasks are decomposed by package/area so each has an
independently verifiable deliverable, but they are **not independent
worktree work** — they all operate on the same `git merge` in progress, so
they execute sequentially in one working tree, in task order. Intermediate
conflict-resolution tasks end with `git add <files>` (staging), not
`git commit`; the merge commit happens once, at the end of Task 11, after
every conflict is resolved.

**Tech Stack:** Yarn workspaces + Lerna (TypeScript/JS), Cargo workspaces
(Rust: `rust/cube`, `rust/cubesql`, `rust/cubestore`), Jest, Docker.

**Spec:** [docs/superpowers/specs/2026-09-22-cube-v1.7.43-sync-design.md](../specs/2026-09-22-cube-v1.7.43-sync-design.md)

## Global Constraints

- Merge source: `v1.7.43` tag fetched from `https://github.com/cube-js/cube.git`
  (the `upstream` remote's SSH URL is not reachable from this machine —
  fetch via HTTPS instead).
- Merge base: commit `465fdf160665cf78e2bee9c964719a96e9a55d12` (tag
  `v1.7.33`) — exact merge-base of `HEAD` and upstream `v1.7.43`.
- All work happens directly on the current branch — it's already an
  isolated worktree branched from `master` for this purpose.
- General conflict-resolution rule: where upstream changed code we haven't
  touched, take upstream's version. Where our fork added something upstream
  doesn't have, keep ours additively. Where both sides changed the same
  lines, preserve the fork's custom behavior while adopting upstream's
  surrounding refactor/structure — never silently drop fork-specific
  behavior to resolve a conflict.
- After every conflict-resolution task, run that package's existing test
  command before staging — if a pre-existing test fails because of the
  resolution, fix the resolution, not the test.
- Do not resolve `yarn.lock` by hand — leave it conflicted until Task 11,
  regenerated via `yarn install`.
