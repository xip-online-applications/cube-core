# Sync cube-core with upstream Cube v1.7.33

## Context

`cube-core` (`xip-online-applications/cube-core`, remote `origin`) is a fork of
`cube-js/cube` (remote `upstream`) with a set of business-specific
customizations layered on top. The fork's `master` branch last synced with
upstream cleanly at tag `v1.6.49` — that tag is the exact git merge-base
between `master` and upstream. Upstream has since moved 615 commits ahead to
`v1.7.33`. This spec covers bringing the fork up to date with `v1.7.33` while
preserving all custom functionality.

Note: the `upstream` git remote is configured over SSH
(`git@github.com:cube-js/cube.git`) but this machine has no working SSH key
for it. HTTPS access to the same repo works fine
(`https://github.com/cube-js/cube.git`) and was used for all investigation
in this spec. The sync branch work should use HTTPS unless SSH access is
fixed separately (out of scope here).

## Investigation findings

- **Divergence point**: merge-base of `master` and upstream `v1.7.33` is
  exactly commit `68b870ea3` (`v1.6.49`). `master` has 232 commits since
  then; upstream has 615.
- **Real custom diff is small**: only **87 files** genuinely differ from
  `v1.6.49` on `master` (full list in Appendix A). The rest of the raw
  diffstat (4364 of 4451 changed files) is committed Rust build cache — see
  next finding.
- **Orphaned build artifacts**: `rust/cubesqlplanner/` and
  `rust/cubeorchestrator/` exist as top-level directories in `master`
  containing *only* `target/` cargo build output (3963 and 401 files
  respectively) — zero real source files. The actual, correct source for
  both lives at `rust/cube/cubesqlplanner/` and `rust/cube/cubeorchestrator/`,
  matching upstream's layout. These two top-level dirs are accidental
  commits of local build output and should be removed and gitignored,
  independent of the version sync itself.
- **`merge-prep` branch** (`origin/merge-prep`) is the team's established
  branch for prior upstream syncs, but it's stale — also last synced at
  `v1.6.49`, and `master` has 216 commits it doesn't have. Not directly
  reusable, but confirms the team's pattern of syncing via a dedicated
  branch before merging to `master`.

## Custom functionality inventory (from the 87-file diff)

- **`cubejs-event-emitter`** (new package): pluggable event emitter
  abstraction with a Redis-backed implementation
  (`RedisEventEmitter.ts`, `DefaultEventEmitter.ts`), used to make core Cube
  processing event-driven.
- **`cubejs-tracer`** (new package): StatsD-based tracing integration.
- **`cubejs-api-gateway`**: WebSocket subscription server
  (`ws/subscription-server.ts`, `ws/local-subscription-store.ts`) with
  tenant-aware subscription handling; extended `meta`/`metaExtended`
  endpoint including `preAggregations` in cube metadata; graphql/query
  adjustments.
- **`cubejs-schema-compiler`**: custom time-dimension granularities
  (`convertToGranularityInSeconds`, `granularityToSeconds`) with additional
  minute-level granularities; case-insensitive filter operators
  (`iStartsWith`, `likeIgnoreCase`) using `LIKE`/`ILIKE` depending on
  context; Postgres `convertTz` fix; pre-aggregation matching by time
  dimension.
- **`cubejs-server-core`**: wiring for the event emitter and tracer into
  `OrchestratorApi`, `RefreshScheduler`, `server.ts`, `optionsValidate.ts`.
- **`cubejs-query-orchestrator`**: `QueryCache`/`QueryOrchestrator`
  adjustments related to the above.
- **`cubejs-backend-native`**, **`rust/cube/cubeorchestrator`**,
  **`rust/cube/cubesqlplanner`**, **`rust/cubestore`**: native module
  loading path fixes, `iStartsWith` filter operator in the Tesseract
  planner, transport/deserialization tweaks.
- **`cubejs-docker`**, `.dockerignore`, `.github/workflows/*`: custom
  Dockerfiles (`dev.Dockerfile`, `transai.Dockerfile`) and CI workflows for
  building/publishing the fork's own images, including native Rust build
  steps.
- **`cubejs-client-core`**, **`cubejs-playground`**,
  **`cubejs-cubestore-driver`**, **`cubejs-backend-shared`**: smaller
  supporting changes (types, query builder utils, driver connection
  handling, time utils).
- Root **`tsconfig.base.json`**, **`tsconfig.json`**, **`package.json`**,
  **`yarn.lock`**: fork-specific config/dependency changes.

All of the above must still work after the sync; see Testing.

## Approach

### 1. Clean up orphaned build artifacts (separate prep commit, direct to `master`)

Before starting the sync, on `master`:

```bash
git rm -r --cached rust/cubesqlplanner/target rust/cubeorchestrator/target
```

Add `target/` (or the specific paths) to `.gitignore` under `rust/` so this
can't recur. Commit and push directly to `master` as its own small commit —
this has no conflict risk with upstream and shrinks the repo before the
much larger merge lands, keeping the sync PR's diff focused on real changes.

### 2. Create the sync branch and merge upstream

```bash
git checkout -b sync/v1.7.33 master
git fetch https://github.com/cube-js/cube.git v1.7.33
git merge FETCH_HEAD
```

Resolve conflicts file by file. Expected hotspots, in rough order of
conflict risk:

- `yarn.lock` — expect a full conflict; do **not** hand-merge it. Resolve
  all other conflicts first, then delete and regenerate via `yarn install`.
- `packages/cubejs-api-gateway/src/ws/*`, `gateway.ts` — subscription
  server and extended meta logic sits directly in code paths upstream also
  touches.
- `packages/cubejs-schema-compiler/src/adapter/*`,
  `compiler/CubeSymbols.ts` — granularity and filter-operator
  customizations vs. upstream's own schema-compiler evolution over 615
  commits.
- `packages/cubejs-server-core/src/core/*` — event emitter/tracer wiring.
- `.github/workflows/*`, `packages/cubejs-docker/*`, `.dockerignore` —
  custom CI/build pipeline vs. upstream's own workflow changes. Note many
  workflow files are already `.bak` (disabled) on `master` — preserve that
  intent rather than reverting to upstream's active versions.
- `rust/cube/cubesqlplanner/**`, `rust/cube/cubeorchestrator/**` — Tesseract
  planner filter-operator changes vs. 615 commits of upstream planner work;
  likely the highest-effort conflict resolution given how actively upstream
  develops Tesseract.
- New packages `cubejs-event-emitter`, `cubejs-tracer` — upstream has no
  equivalent, should merge in without conflict.

### 3. Version bump

Update `lerna.json` and root `package.json` version to a `1.7.33` base,
following the repo's existing convention of a `cube X.Y.Z` commit after each
sync (see e.g. commit `70df565de "cube 1.6.49"`).

### 4. Build and automated validation

In order, all must pass before moving on:

```bash
yarn install        # regenerates yarn.lock cleanly post-merge
yarn tsc             # full monorepo TypeScript compilation
yarn build
yarn lint
```

Rust: build `rust/cube` (and `rust/cubestore` if its conflict touched
anything), checking `rust-toolchain` compatibility between `v1.6.49` and
`v1.7.33` — upstream may have bumped the required Rust toolchain version
over 615 commits.

Then run `yarn test` in each touched package (the ~13 areas in the
inventory above), plus a full monorepo test sweep per the repo's normal
`yarn test` command.

### 5. Manual smoke check

Beyond automated tests, manually verify the business-critical custom flows
still work end to end, using the dev server / docker setup:

- WebSocket subscriptions: open a subscription, confirm it receives
  updates, confirm unsubscribe/renew behavior.
- A query using a custom minute-level granularity
  (`convertToGranularityInSeconds` path).
- A query using `iStartsWith` / case-insensitive `LIKE` filtering.
- Extended `meta` endpoint returning `preAggregations` in cube metadata.

### 6. Push and open a PR

Push `sync/v1.7.33` to `origin` and open a PR into `master`. PR description
should cover: version bumped to 1.7.33, summary of conflict resolution per
hotspot area above, confirmation of automated + manual validation, and a
pointer to this spec.

## Out of scope

- Fixing SSH access to the `upstream` remote (HTTPS works and is sufficient
  for this task).
- Any new features or refactors beyond what's needed to reconcile the merge
  and keep existing custom functionality working.
- Re-enabling the `.bak` GitHub workflow files — they stay disabled as they
  currently are on `master` unless the merge itself requires touching them.
